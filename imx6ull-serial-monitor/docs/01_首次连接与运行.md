# 首次连接：先分清三台“Linux”

| 环境 | 实际运行位置 | 作用 |
|---|---|---|
| Win11 | 电脑 | CH340 驱动、串口终端、PC 监测程序、MfgTool |
| VirtualBox Ubuntu / WSL | 电脑 CPU | 编译 ARM 应用和驱动、制作根文件系统 |
| 开发板 Linux | i.MX6ULL CPU | 运行 ARM 程序、访问传感器、通过 UART 通信 |

在虚拟机能登录 Ubuntu，不代表开发板已经开机或已安装系统。

## 1. 在电脑上跑模拟

在 Windows PowerShell 执行（项目路径包含中文时保留引号）：

```powershell
cd 'D:\linux项目\imx6ull-serial-monitor'
py -3 host\monitor.py --simulate --seconds 12
py -3 host\dashboard.py
```

模拟界面会显示明确的 PYTHON SIMULATOR 握手信息。把光照阈值设成 100，等待一个采样周期，应出现告警及 `logs/events.sqlite3` 记录。恢复成 3000，演示数据仍会周期性制造光照/运动告警。

## 2. 找对 USB 接口

按指南第 5 章：ALPHA 的 `USB_TTL` 连接 CH340，用于调试串口；`USB_SLAVE/OTG` 接 SoC USB 控制器，用于烧录/USB Gadget。首次查看启动日志接 USB_TTL；烧写 eMMC 时另接 USB_SLAVE/OTG。请按实际板上丝印核对，勿把两个接口混用。

正常接板电源，USB 数据线连接电脑与 USB_TTL。检查 JP5 对应 UART1 的跳线帽，不要在不确定的情况下改动其他跳线。板上 Mini-USB 需要能传数据的线。

在 Win11 设备管理器查看“端口(COM 和 LPT)”。应看到 USB-SERIAL CH340 或相似设备及 COM 编号。若是未知设备，使用配套资料里的 CH340 驱动或芯片厂家官方驱动。不要把软件生成的 ELTIMA COM1/COM2 当成开发板。

电脑初次检查只看到了 ELTIMA COM1/COM2，没有枚举到真实 CH340；这只是当时的状态，连接后重新检查。

```powershell
py -3 host\monitor.py --list
```

如果 VirtualBox 捕获了 CH340，先在虚拟机 USB 菜单释放它，让 Windows 主机使用。首轮运行 PC 客户端时无需给 WSL 配置 USB 直通。

## 3. 看到开发板启动日志

用 SecureCRT/PuTTY 或其他串口终端打开真实 COM，参数 115200、8 数据位、无校验、1 停止位、无软件/硬件流控。打开终端后按板上复位键。

预期能看到 U-Boot、Starting kernel、内核日志或登录提示。按固件说明登录；本项目不假设所有固件的 root 密码相同。若未出现 login，但有 shell 提示，按回车后执行：

```sh
uname -m
uname -r
cat /proc/device-tree/model
cat /proc/cmdline
```

物理板上通常看到 ARM 架构；WSL/虚拟机常见 x86_64。若是 Ubuntu 电脑的欢迎信息而不是板卡串口日志，仍在错误的环境。

若完全无字符：先排查接口、数据线、驱动、串口占用、VirtualBox 直通、电源、JP5、启动拨码，而不是立即刷机。只有系统确实损坏/缺失时才看烧录文档。

## 4. 先上传应用，暂不修改内核

优先使用 `release/serial-monitor-board.tar.gz`。有 U 盘时把它放入 U 盘，在板上根据实际挂载路径复制到 `/tmp`；不要把 `/dev/sda1` 当作固定设备名。

只用 USB 串口也可上传：板端已登录 root shell且 `base64`、`sha256sum` 可用时，关闭串口终端，然后在 Win11 执行：

```powershell
py -3 host\upload.py --port COM7
```

上传工具 v2 通过已有 shell 启动按字节计数的接收器，逐块确认 Base64 数据，末尾做 SHA256 核对；这不是 bootloader 烧录工具，也不能在 U-Boot 提示符或登录密码提示处使用。若途中中断，重新打开终端，按 Ctrl+C，执行 `stty sane`，再重新上传。还需要 `stty`、`dd`、`wc`、`cat`、`mv`；脚本会检查。没有这些命令时改用 U 盘/SD 文件拷贝，或先补齐工具。修复说明见 `09_串口上传故障与v2修复.md`。

上传成功后重新打开串口终端，在板上执行：

```sh
cd /tmp
tar xzf serial-monitor-board.tar.gz
sh /tmp/serial-monitor/scripts/install-board.sh
```

安装位置 `/opt/serial-monitor`；配置与告警默认 `/var/lib/serial-monitor`。用 `mount` 确认 `/var/lib` 在持久介质上；若它是 tmpfs，选择 eMMC 上的持久目录并用 `MONITOR_STATE=/实际路径` 启动。只读根文件系统也需单独选择可写数据目录。

## 5. 真串口 + 模拟传感器

在开发板串口 shell 执行：

```sh
sh /opt/serial-monitor/scripts/run-session.sh --mock
```

有 5 秒时间关闭串口终端，然后打开 PC 监测程序并连接同一 CH340 COM：

```powershell
py -3 host\monitor.py --port COM7 --seconds 20
```

这次 `mock` 数据在真正 ARM 程序里生成，通过实体 UART/CH340/USB 传输，和完全 PC 模拟是两种测试。默认 300 秒后板端自动退出；PC 的 `--seconds 20` 只是 20 秒后断开 PC，不会自动终止板端。

立即恢复终端的方法：先关闭其他 PC 串口程序，再执行 `py -3 host\monitor.py --port COM7 --stop`，或者在桌面界面点击“退出板端程序 / 恢复终端”。随后关闭 PC 客户端、重新打开串口终端并按回车。`--silence` 只消音，不退出。

## 6. 接入真实传感器

完成驱动与 DT 部署后确认存在 `/dev/mon_ap3216c` 和 `/dev/mon_icm20608`。按键事件编号不可固定猜测，通过 `/proc/bus/input/devices` 找到 gpio-keys 对应 eventN：

```sh
sh /opt/serial-monitor/scripts/run-session.sh --key /dev/input/eventN
```

把 eventN 替换成实际设备；不使用按键时省略 `--key`，仍可在 PC 消音。真实模式下缺少传感器会报错退出，绝不静默切换成模拟数据。
