# ALPHA + eMMC：烧录、构建与部署

先读 `01_首次连接与运行.md`。本文把“恢复整套系统”和“更新项目应用”分开，不能把普通应用直接当作 `.imx` 镜像烧入启动区域。

## A. 选择正确的操作

| 当前情况 | 操作 |
|---|---|
| USB_TTL没出现COM | 先排查线、CH340驱动、USB接口、虚拟机USB捕获 |
| 有COM但完全无启动日志 | 核对电源、JP5、115200、拨码、复位；尚不能据此认定系统损坏 |
| 能进入开发板Linux | 先上传项目应用并跑 --mock，不必重刷eMMC |
| 有U-Boot但内核/根文件系统损坏 | 按对应板型、底板版本的配套MfgTool恢复 |
| 系统正常，想运行真实传感器 | 构建匹配内核的驱动，调整设备树并部署 |

eMMC整盘恢复会重新分区/覆盖原系统及其中的数据。先保存现有需要的文件和 `printenv` 输出。此项目没有自动执行刷机，也未改变你开发板的拨码、U-Boot环境或系统分区。

## B. Win11 下使用配套 MfgTool 恢复系统

### B1. 核对底板版本与固件

你已确认是ALPHA、eMMC，仍要看底板丝印版本号。资料包明确区分：

- ALPHA V2.4之前（与Mini V2.2之前归组）；
- ALPHA V2.4及以后（与Mini V2.2及以后归组）。

教程镜像在资料包 `08、系统镜像/08、系统镜像/02、教程系统镜像/` 对应子目录中，各有 `mfgtool(study).7z`。先阅读同目录 `mfgtool(study)说明.txt`，再解压到一个独立的短路径。不能仅凭内核版本相同就混用不同底板的U-Boot/DTB。

本机还存在 `05、开发工具/05、开发工具/04、正点原子MFG_TOOL出厂固件烧录工具/mfgtool` 和 `mfgtool_2`。未核定两者与实物底板的映射，不要按名字猜测哪份适合你；以快速体验手册和包内说明为准。

### B2. 连接与进入下载模式

1. 正常供电。按配套包提示处理显示屏连接；不要带电插拔屏幕排线。
2. USB_TTL连电脑看日志；**再用USB数据线连接USB_SLAVE/OTG到电脑，用于实际烧录**。只接USB_TTL不能由MfgTool烧eMMC。
3. 按实物丝印/对应手册把BOOT拨码设为USB下载模式。这里不提供脱离板号的固定拨码位图。
4. 按教程下载模式说明处理TF卡，复位/重新上电。不要把正常eMMC启动和ROM USB下载模式混为一谈。
5. 将下载设备留给Windows，避免VirtualBox自动捕获。设备应枚举为对应i.MX下载/HID设备；此时不是CH340 COM端口。

### B3. 选择eMMC脚本并开始

教程镜像说明中给出的eMMC脚本是：

```text
study-Mfgtool2-eMMC-ddr512-eMMC.vbs
```

已检查到的出厂工具脚本名是 `Mfgtool2-eMMC-ddr512-eMMC.vbs`。应在所选固件包内部使用对应脚本，不要把一个包的脚本和另一个包的 `Profiles` 混搭。eMMC脚本里的DDR512要与核心板规格相符；本资料对应eMMC核心板通常为512MB DDR，实物仍应核对。

运行脚本后确认目标设备识别，再点击Start；等待完整成功提示后Stop/关闭。若`.vbs`无法启动，可阅读该脚本并从其所在目录运行它指定的MfgTool2命令，保持参数完整；这不等于随意双击exe选择默认NAND参数。旧版工具在你的Win11上尚未实测，遇到驱动/脚本问题先看工具日志和包内说明。

烧录后把BOOT改回eMMC并复位。先通过USB_TTL确认U-Boot和Linux日志。教程包说明要求eMMC烧完后参考其`【EMMC-bootcmd-bootargs】`说明设置启动参数，以包内实际文件为准。

**不要直接复制网上的 `root=/dev/mmcblk1p2` 或固定DTB名字。** 指南第39章曾使用这些值，但你所选固件的分区布局/环境可能不同。先在U-Boot执行 `printenv bootcmd bootargs`，结合包内说明核对实际内核文件、DTB文件、根分区和`console=ttymxc0,115200`，确认后再保存。初次接板保留串口console便于排错。

### B4. 明白烧进去的是什么

MfgTool一般先通过USB把临时引导/内核/设备树等下载到DDR，启动烧录环境，再根据`ucl2.xml`把U-Boot、zImage、DTB和rootfs写入eMMC。`firmware`中的临时烧录系统和`files`中的最终系统用途不同。现阶段优先使用已匹配的整包，不把普通项目可执行文件替换到这些位置。

## C. 构建用户态应用

交付包的实际预编译状态见`06_测试报告.md`。若包含`release/arm/monitor`，可直接进入D节验证，不需要先重新搭建交叉工具链。

### C1. Ubuntu虚拟机 / WSL中使用配套Linaro

解压资料中的`gcc-linaro-4.9.4-2017.01-x86_64_arm-linux-gnueabihf.tar.xz`到Linux家目录；工具链是Linux可执行程序，不能在Win11 PowerShell里直接运行。

```sh
# 以下命令在Ubuntu/WSL执行。路径按自己的解压位置调整。
export PATH="$HOME/toolchains/gcc-linaro-4.9.4-2017.01-x86_64_arm-linux-gnueabihf/bin:$PATH"
arm-linux-gnueabihf-gcc --version
cd /path/to/imx6ull-serial-monitor
make -C board CROSS_COMPILE=arm-linux-gnueabihf-
file board/monitor
mkdir -p release/arm
cp board/monitor release/arm/monitor
python3 scripts/make-package.py
```

GCC默认生成动态链接应用，要确认板端有兼容的ARM硬浮点动态加载器和运行库；若希望静态应用，可在本项目Makefile调用时覆盖CFLAGS包含`-static`，并保留`-pthread`等已有编译参数。本次提供的Windows构建脚本会使用配套Linaro库静态链接，减少板上运行库版本依赖。

WSL访问Windows项目通常是`/mnt/d/linux项目/imx6ull-serial-monitor`。建议复制源码到Linux用户目录后编译内核，避免共享目录文件权限/符号链接和性能问题。不要把VirtualBox共享文件夹中的x86程序当成ARM程序。

### C2. Win11直接交叉构建

`scripts/build-windows.py`调用Zig 0.13.0自带的Clang/LLD，读取你资料里的Linaro 4.9.4 ARM头文件/库并静态链接，不需要安装系统服务或修改PATH。需要先准备Zig官方发行包和原Linaro压缩包：

```powershell
py -3 scripts\build-windows.py --zig 'C:\tools\zig\zig.exe' --linaro '你的完整路径\gcc-linaro-4.9.4-2017.01-x86_64_arm-linux-gnueabihf.tar.xz'
py -3 scripts\make-package.py
```

Zig官方版本地址：<https://ziglang.org/download/0.13.0/release-notes.html>。项目不把庞大的工具链复制到交付包；按实际路径传参。`build/linaro`与缓存是中间产物，不部署到开发板。

## D. 部署应用：只用USB串口也可以

先在串口终端登录板端root shell并关闭终端，再在Windows执行：

```powershell
py -3 host\upload.py --port COM7
```

上传成功后重新打开终端，在板端执行：

```sh
cd /tmp
tar xzf serial-monitor-board.tar.gz
sh /tmp/serial-monitor/scripts/install-board.sh
sh /opt/serial-monitor/scripts/run-session.sh --mock
```

按提示关闭串口终端，用PC客户端连接。该阶段不要求传感器驱动、不改设备树、不重刷eMMC。安装脚本只更新`/opt/serial-monitor`内项目文件，保留旧应用为`monitor.previous`，不修改启动服务。

## E. 构建驱动和设备树

必须使用与实际运行内核匹配的源码、配置、编译器和Module.symvers；`uname -r`都叫4.1.15也不代表模块一定兼容。推荐从资料中与底板版本对应的教程源码开始，完整编译内核，再用它编译模块。若使用出厂内核，也必须取得其准确构建配置。

1. 备份正确的`imx6ull-alientek-emmc.dts`。检查节点确实是`&i2c1/ap3216c@1e`与`&ecspi3/icm20608@0`，以及GPIO1_IO20片选引脚复用。
2. 把项目`drivers/serial-monitor.dtsi`复制到内核`arch/arm/boot/dts/`，在板级DTS末尾加：

```c
#include "serial-monitor.dtsi"
```

3. 这是编译时合并片段，不是运行时DT overlay。传感器`compatible`改为`study,mon-ap3216c`和`study,mon-icm20608`，避免旧驱动绑定。SPI片选使用控制器框架管理的`cs-gpios`，不能同时手动申请相同GPIO做片选。
4. 确认内核启用I2C、SPI及对应i.MX控制器、MODULES、GPIO、gpio-leds、gpio-keys、INPUT_EVDEV、DEVTMPFS。原厂板级DTS中蜂鸣器由gpio-leds节点管理；精简教程DTS可能没有它，需要参考本机原厂DTS补齐，而非让两个驱动抢占GPIO。
5. 在Ubuntu/WSL执行，下面`KDIR`必须换成自己的准确源码路径：

```sh
export KDIR=/home/你的用户名/linux-imx-对应版本
# 首次按板型加载配置；已有自定义配置时先备份，勿反复用defconfig覆盖。
make -C "$KDIR" ARCH=arm CROSS_COMPILE=arm-linux-gnueabihf- imx_alientek_emmc_defconfig
make -C "$KDIR" ARCH=arm CROSS_COMPILE=arm-linux-gnueabihf- -j4 zImage dtbs modules
make -C drivers KDIR="$KDIR" CROSS_COMPILE=arm-linux-gnueabihf-
```

得到`drivers/mon_sensors.ko`和新DTB。**本次交付没有宣称该模块已经在你的运行内核上编译/加载成功**；本机没有可用的已配置内核构建环境，仍需在上述环境完成。

DTB应部署到U-Boot实际加载的位置，先保存原DTB，确认`printenv`中的启动路径；不能假设所有固件都从同一个FAT分区或同一个`/boot`目录加载。若首次改内核/DTB，先保留原固件恢复包与启动环境记录。项目不提供自动覆盖未知分区的脚本。

重启到新DTB后，在板端加载模块并检查：

```sh
insmod /实际路径/mon_sensors.ko
dmesg | tail -n 30
ls -l /dev/mon_ap3216c /dev/mon_icm20608
ls /sys/class/leds
cat /proc/bus/input/devices
```

驱动应报告AP3216C ready、ICM20608 ready。若设备节点不自动创建，先检查devtmpfs/mdev配置，勿猜测主次设备号。

运行真实采集：

```sh
sh /opt/serial-monitor/scripts/run-session.sh --key /dev/input/eventN
```

## F. 长期运行时释放UART1

临时会话保留恢复能力，适合学习；长期运行应彻底分离控制台。先保存U-Boot环境和`/etc/inittab`：

- 核对实际bootargs来源，移除`console=ttymxc0,...`及指向同一口的earlycon/earlyprintk，检查DT chosen/stdout-path和系统是否仍创建默认串口console。
- BusyBox/SysV停用对应ttymxc0的getty/respawn行；systemd系统停用对应serial-getty服务。只处理实际存在的启动机制。
- 确认没有其他shell/getty/应用读写该口，再设置独立服务启动monitor。
- 启动服务需有失败重启、日志轮转、退出关闭报警输出的策略；保留U-Boot恢复入口或第二调试口。

项目没有自动永久修改控制台，也没有安装未经板端验证的开机服务。先把临时会话跑通，再根据实际rootfs选择init脚本或systemd unit。
